# PR 전 검증

구현과 커밋을 마친 뒤, **푸시하고 PR 을 만들기 전에** 변경 사항을 검증하고 결과를 PR 에 넣을 수 있는 형태로 정리해요.

> 프로젝트의 `CLAUDE.md` / `AGENTS.md` 에 검증 규칙이 있으면 그것을 우선해요.

## 1. 변경 범위 파악

- 기본 브랜치와 비교해 바뀐 파일을 확인해요. (`git diff <default>...HEAD --stat`)
- 변경을 다음 중 어디에 해당하는지 분류해요. 여러 개일 수 있어요.

| 분류 | 예 | 검증 방법 |
|------|----|-----------|
| 코드 | 앱/라이브러리 소스 | 2. 로컬 검증 |
| 화면/동작 | UI, 라우팅, 폼, API 응답 | 2 + 3. 브라우저 검증 |
| 기본 브랜치에 있어야 동작 | GitHub Actions, 이슈/PR 템플릿, 레포 설정 | 4. 머지 후 확인 |
| 문서 | README, 주석 | 링크/렌더링 확인 |

## 2. 로컬 검증

프로젝트가 제공하는 명령을 찾아 실행해요. 명령을 지어내지 말고 실제로 정의된 것만 써요.

- `package.json` 의 `scripts` (예: `lint`, `check-types`/`typecheck`, `test`, `build`, `format:check`)
- `Makefile`, `justfile`, `pyproject.toml`, `Cargo.toml`, CI 워크플로우(`.github/workflows/`)에서 쓰는 명령
- 모노레포라면 바뀐 패키지만 대상으로 실행해도 돼요. (예: `turbo run lint --filter=...[<default>]`)

실행할 수 없는 검증(파일 형식 확인, 스크립트 로직 등)은 가능한 범위에서 시뮬레이션해요.
예: YAML 파싱, 워크플로우 스크립트를 샘플 입력으로 실행.

실패하면 **고치고 다시 커밋**한 뒤 검증을 반복해요. 고칠 수 없으면 사용자에게 보고해요.

## 3. 브라우저 검증 (화면/동작이 있는 변경)

- 브라우저 자동화 MCP(예: Chrome DevTools MCP)가 연결되어 있으면 개발 서버를 띄우고 **변경한 기능을 직접 사용**해 봐요.
  - 정상 흐름과 주요 예외 흐름(빈 값, 오류 응답 등)을 확인해요.
  - 콘솔 오류와 실패한 네트워크 요청이 없는지 확인해요.
- 로그인, 2단계 인증, 결제 정보 입력은 **사용자가 직접** 해요. 비밀번호나 인증 코드를 입력하지 않아요.
- 테스트 대상 탭만 다루고 다른 탭은 건드리지 않아요.
- MCP 가 없으면 검증하지 못한 항목으로 남기고, 사용자가 확인할 절차를 적어요.

## 4. 머지 후 확인이 필요한 변경

기본 브랜치에 있어야 동작하는 변경은 PR 단계에서 완전히 검증할 수 없어요.

- 로컬에서 가능한 부분(파싱, 스크립트 시뮬레이션)은 미리 확인해요.
- PR 에 **머지 후 확인 절차**를 단계별로 적어요.
- 머지 후 실제로 확인하고 결과를 PR 이나 이슈에 댓글로 남겨요.
- 확인용으로 만든 테스트 이슈/PR 은 결과를 댓글로 남기고 닫아요. (이슈는 `not planned`)

## 5. 결과 정리

PR 본문의 검증 섹션에 그대로 넣을 수 있도록 정리해요.

```markdown
- [x] `pnpm lint` 통과
- [x] `pnpm build` 통과
- [x] 브라우저에서 로그인 → 대시보드 이동 확인 (Chrome DevTools MCP)
- [ ] 모바일 화면 — 확인하지 못함 (MCP 에뮬레이션 미지원)

**머지 후 확인**
1. 새 이슈를 `📋 새 할 일` 양식으로 생성
2. 작업 유형에 맞는 라벨이 붙는지 확인
```

- 직접 확인한 것만 `[x]` 로 체크해요.
- 건너뛴 것, 실패한 것, 확인하지 못한 것을 숨기지 않고 이유와 함께 적어요.
